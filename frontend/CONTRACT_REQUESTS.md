# Contract requests — frontend → Codex

Gaps found while building the frontend against `contracts/openapi.yaml`. The frontend
has **not** changed the contract and does **not** call anything not declared there. Each
item below records what the UI needed, why, and either the resolution shipped in the
Phase 1B freeze or the workaround still in place.

Status legend: `RESOLVED` = accepted in the frozen contract and consumed by the UI ·
`WORKED-AROUND` = deferred by Codex; the UI ships without it.

---

## CR-001 — Run listing / "most recent run" lookup — `WORKED-AROUND`

**Need.** The operations dashboard opens on "the current run". The contract has no
`GET /runs` (list) and no "latest run" lookup, so there is no way to find a run
without already holding its `run_id`.

**Workaround.** The frontend stores the most recently created `run_id` in
`localStorage` and calls `GET /runs/{run_id}`. A browser with cleared storage sees an
empty state that routes to regulation intake.

**Requested.** `GET /api/v1/runs` returning `{ items: Run[], total: int }`, ideally with
`limit` and `state` query parameters.

**Status.** Deferred in the Phase 1B freeze to preserve the eight-path boundary. The
`localStorage` workaround stays.

---

## CR-002 — Run state-transition history (timeline) — `RESOLVED`

**Need.** Run detail must show "visible processing stages" and a timeline of state
transitions with timestamps. Phase 1A's `Run` exposed only the *current* `state`, so
history was not retrievable and the UI could only log what it observed itself.

**Resolved.** `Run.transitions` is a required, authoritative, oldest-to-newest array of
`RunTransition` records (`from_state`, `to_state`, `occurred_at`, `reason`, `actor`),
with a null `from_state` on the first entry.

**Consumed by.** `RunDetailPage` renders the array in the order the API returns it,
including the initial `INGESTED` entry, with the recorded actor, timestamp and safe
reason label. `useRunPolling` no longer records a client-observed history, and the
"transitions before this page was opened are missing" copy is gone. Reason and actor
are treated as safe backend labels; no agent reasoning is displayed.

## CR-003 — Recoverable-failure detail — `RESOLVED`

**Need.** `run-states.md` says `FAILED_RECOVERABLE` should be shown "with retry
state", but Phase 1A exposed the enum value and nothing else.

**Resolved.** Nullable `Run.recovery` carries `recovery_available`,
`checkpoint_state`, `attempt_count`, `last_error_code` and `last_error_message`. The
contract guarantees a non-null checkpoint whenever recovery is available, and the
error fields are sanitized by the backend.

**Consumed by.** A recovery panel on run detail and the dashboard's recovery notice
render availability, checkpoint state, attempt count and the sanitized error code and
message. A null `recovery` says so plainly instead of inventing a value.

---

## CR-004 — Change / version detection result — `RESOLVED`

**Need.** Regulation intake is specified to show the "detected version/change
result", which `Regulation` did not carry.

**Resolved.** Nullable `Run.change_detection` carries `source_sha256`,
`previous_source_sha256`, `changed` and `detected_at`, with lowercase SHA-256 values.

**Consumed by.** Intake and run detail show changed / unchanged / new, the detection
time, and both hashes shortened for reading with the complete value exposed to
assistive technology and as a hover title. A null result is reported as not returned.

## CR-005 — Approval lookup by id — `WORKED-AROUND`

**Need.** The approval screen is reachable by URL (`/approvals/{approval_id}`). There
is no `GET /approvals/{approval_id}`; the only way to read an approval is to find it
inside `Run.pending_approvals`, and decided approvals disappear from that array.

**Workaround.** The approval screen still requires a `run` query parameter and locates
the approval inside `GET /runs/{run_id}`. After a decision it renders the `Approval`
returned by `POST /approvals/{approval_id}/decision`; a hard reload after deciding
shows a "no longer pending" state that points at run detail rather than the decision
record.

**Requested.** `GET /api/v1/approvals/{approval_id}` returning `Approval`.

**Status.** Deferred in the Phase 1B freeze. The `?run=` requirement stays.

## CR-006 — Audit package download — `RESOLVED`

**Need.** The audit view specifies a "download audit package" control, and
`AuditReport.audit_package_url` was undocumented as to whether it was a signed URL, a
relative API path, or a GCS URI.

**Resolved.** A non-null `audit_package_url` is defined as a short-lived, absolute
HTTPS signed download URL generated by the backend. It is response-only; clients never
submit it.

**Consumed by.** `isSafeAuditPackageUrl` still validates the value before it reaches an
`href` — absolute `https://` with a non-empty host, everything else refused — and the
control explains which case applies when it is disabled. The offline mock issues no
signed URL, so it returns `null` rather than an invented target.

## CR-007 — Scores on `FindingSummary` — `RESOLVED`

**Need.** The findings list must show evidence strength, source authority,
interpretation confidence, operational severity and the human-review requirement.
Phase 1A only carried the last two on `FindingSummary`, forcing one
`GET /findings/{finding_id}` per listed row.

**Resolved.** `FindingSummary.scores` is required.

**Consumed by.** `FindingsPage` reads every score column straight off the list
response. The per-row hydration hook is deleted, and a regression test asserts the
screen never calls `getFinding`.

---

## CR-008 — Action → finding lookup — `RESOLVED`

**Need.** The approval screen receives an `action_id` and must show the finding that
action came from. Phase 1A had no way to get there, so the screen fetched findings
one at a time until it found a matching `proposed_action.action_id`.

**Resolved.** No ninth path was added. Instead `Approval.finding_id` is required,
which is what the approval screen actually needed.

**Consumed by.** `ApprovalPage` calls `api.getFinding(approval.finding_id)` once. The
O(findings) scan is deleted, and a regression test asserts the screen never lists
findings.

---

## CR-009 — Findings pagination — `RESOLVED`

**Need.** `GET /runs/{run_id}/findings` returned `{ items, total }` with no `limit` /
`offset`, so a run over a 300-document corpus had no way to page.

**Resolved.** `limit` (default 50, range 1–100) and `offset` (default 0, minimum 0) are
accepted. `items` is the selected page; `total` and `by_severity` describe the complete
result matching the active filters before pagination.

**Consumed by.** The HTTP adapter sends `severity`, `q`, `limit` and `offset` (including
`offset=0`). The findings screen shows the visible range, the filtered total, the
filtered severity counts and previous/next controls, and resets the offset whenever a
severity or search filter changes.
